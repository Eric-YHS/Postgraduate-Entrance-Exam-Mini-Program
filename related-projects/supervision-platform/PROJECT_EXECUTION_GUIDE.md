## 1. 项目目标与产品边界

### 1.1 产品目标

本项目是一个面向考研学习过程的督学平台，目标是把教师管理、学生学习、课程与商品、订单与权益、学习计划、任务完成、自测、入学测评、社区审核、学习事件和未来的 AI 能力放在同一个可审计、可扩展、可部署的系统中。

系统不是单纯的静态页面，也不是只依赖浏览器 localStorage 的演示程序。正式设计目标是：

- 有服务端身份认证和会话管理。
- 有数据库作为生产数据的真实来源。
- 有明确的角色、资源归属和权限矩阵。
- 有服务端业务规则，前端不能单独决定关键权益。
- 有数据库迁移、约束、事务、唯一索引和锁。
- 有健康检查、就绪检查、日志、审计、备份和恢复流程。
- 有可重复的构建、测试和上线前验证。
- AI 输出只能作为受规则约束的草案或建议，涉及权益、考试结果、公开内容和学习计划的结果必须经过服务端规则和人工确认。

### 1.2 两种运行模式

前端目前存在两种运行模式：

**API/生产模式**：当 `VITE_API_BASE_URL` 存在，或 Vite 以生产模式构建时，`isApiConfigured()` 返回 true。此时浏览器应通过 API 与 Fastify 后端和 PostgreSQL 交互，认证使用 HttpOnly Cookie，核心数据以服务端为准。

**本地演示模式**：开发环境没有配置 API 时，部分旧版功能仍使用 localStorage 保存演示数据。该模式只适合本机原型开发、界面调试和无敏感数据测试，不能用于真实多用户、真实支付、真实学生档案或正式上线。

任何新增功能必须优先设计 API 模式。只有明确属于离线草稿、浏览器临时偏好或尚未完成迁移且经过记录的字段，才可以保留本地存储。

### 1.3 独立的专业课 AI 原型

同级目录 `专业课AI机器人` 是另一个 Python/HTML 原型服务，包含 `server.py`、`student.html`、`teacher.html`、`data`、模型配置示例和浏览器验收脚本。它有自己的 README、`.env` 和启动脚本。

不要把以下内容误认为主项目源码：

- `专业课AI机器人/chrome-*` 浏览器审计缓存目录。
- `专业课AI机器人/*audit*` 截图和脚本。
- `专业课AI机器人/dump_*` 临时导出文件。
- 主项目与 AI 原型之间没有自动共享数据库或登录会话，除非明确新增接口和集成设计。

- `server/src/bootstrap-admin.js`：一次性创建初始管理员，完成后必须清除临时密码环境变量。

## 4. 身份认证与会话执行逻辑

### 4.1 登录流程

1. 前端调用 `POST /api/auth/login`，请求通过 `src/api.js` 发送，设置 `credentials: 'include'`。
2. 后端使用 Zod 校验手机号和密码长度。
3. 后端只查询状态为“启用”的账号。
4. 使用 Argon2id 验证 `password_hash`。
5. 登录失败统一返回失败信息，不泄露账号是否存在。
6. 登录成功后签发 JWT，并写入 HttpOnly `session` Cookie。
7. Cookie 使用 `SameSite=Lax`；生产环境必须 `secure=true`；路径为 `/`；有效期当前为 7 天。
8. 更新 `last_login_at`，写入登录审计日志。
9. 前端保存当前会话的非敏感账号摘要，不保存密码、JWT 或服务端密钥。

### 4.2 每次请求认证流程

1. `verifySession` 读取 `request.cookies.session`。
2. 使用 `SESSION_SECRET` 验证 JWT。
3. 以 JWT 中的 `accountId` 查询数据库中的当前账号。
4. 如果账号不存在、被停用或状态不为“启用”，立即拒绝请求。
5. 使用数据库中的最新 role、student_id、status 和 must_change_password 覆盖 JWT 中的可变权限信息。
6. 普通业务请求经过 `app.auth`；如果 `mustChangePassword=true`，返回 403 并要求先改密。
7. `/api/auth/me` 和 `/api/auth/change-password` 使用 `authBase`，保证被强制改密账号仍可查看身份并完成改密。

这意味着：停用账号后，旧 JWT 不能继续访问业务接口；不允许只验证 JWT 而不回查账号表。

### 4.3 改密和管理员重置密码

- 学生或管理员主动改密必须提交当前密码和符合长度要求的新密码。
- 管理员重置他人密码必须使目标账号下次登录强制改密，除非有明确受控的产品规则允许取消。
- 密码永远不能写入日志、审计 metadata、前端状态、localStorage 或 API 返回。
- 临时 bootstrap 密码只通过环境变量传入，初始化后立即清理。

### 4.4 登录保护

登录接口有单路由限流：最多 10 次/15 分钟。公开登记接口有单路由限流：最多 5 次/15 分钟。全局 API 限流当前为 120 次/分钟。

后续增强方向：按 IP 和账号标识组合限流、失败计数告警、验证码或 WAF、登录设备和会话撤销、refresh token 轮换、多因素认证。

## 5. 角色、权限与数据归属

### 5.1 当前角色

当前后端角色包括：`admin`、`teacher`、`assistant`、`operator`、`student`。

权限决策必须在后端执行，前端隐藏按钮不构成权限控制。

### 5.2 当前权限概览

- `admin`：账号管理、审计日志、全部教师能力和系统管理。
- `teacher`：课程、商品、订单审核、题库、试卷、考试分发、学生计划和社区审核。
- `assistant`：当前可读取登记、学生列表等部分管理数据，并可审核社区帖子；具体范围必须在正式权限矩阵中继续收紧和确认。
- `operator`：当前可读取登记、学生列表等运营数据；不得默认获得课程发布、订单审核、账号管理或学生敏感字段写权限。
- `student`：只能访问自己的学生资料、自己的计划、自己的任务、自己的自测、自己的订单和被授权课程；不能访问其他学生数据和管理接口。

### 5.3 学生资源归属

`requireStudent` 只允许 student 账号调用学生本人资源接口，并要求 `studentId` 存在。

`canAccessStudent(request, studentId)` 对学生账号进行资源 ID 比较；管理角色可根据路由权限访问，但不能因此绕过字段级敏感数据保护。

学生自助 PATCH 只能修改允许字段，如姓名、邮箱、收货信息、学校和目标分。状态、付费状态、paidUntil、角色、权限、权益等字段只能由受控管理接口修改。

### 5.4 权限修改标准

任何新路由必须在实现前写明：

- 谁可以调用。
- 谁可以读取哪些字段。
- 谁可以修改哪些字段。
- 是否需要资源归属检查。
- 是否需要状态检查。
- 是否需要审计。
- 是否需要幂等或并发保护。

如果权限矩阵不清楚，不得使用“所有 staff 都可访问”作为默认方案。应选择最小权限，并在本文件记录待确认项。

## 6. 课程、商品、订单与权益流程

### 6.1 课程创建

1. 教师或管理员提交课程名称、受众、分类、描述、定价和状态。
2. Zod 校验长度、枚举、价格和状态。
3. 付费课程价格必须大于 0。
4. 服务端创建为草稿，返回标准课程 DTO。
5. 前端通过归一化器将 DTO 转为展示模型。
6. API 模式下不把服务端课程写入 localStorage。

### 6.2 课程发布

发布前必须由服务端检查：课程存在、描述不为空、付费课程价格大于 0。发布状态不能由前端直接改写数据库。

课程下架或回退草稿后，学生端可见范围必须立即重新计算；已有学习历史和订单记录不能被无审计地删除。

### 6.3 商品创建和发布

商品可以是单科课程、组合套餐或资料包。商品发布前必须满足：

- 付费商品价格大于 0。
- 至少绑定一门课程。
- 绑定课程全部存在且为“已发布”。
- 课程 ID 列表经过 UUID 校验和数量限制。
- 商品状态只能使用允许枚举。

商品发布不能只检查课程存在，因为草稿课程不应被购买或授予访问权益。

### 6.4 订单流程

1. 学生请求购买商品。
2. 服务端根据商品 ID 查询当前商品和服务端价格，不能信任前端金额。
3. 商品不存在或已下架时拒绝。
4. 免费商品创建为已支付订单，并通过权益事务授予访问权。
5. 付费商品创建为待支付或待审核订单；同一学生与商品的待处理订单通过唯一索引防重复。
6. 管理员或教师审核待处理订单。
7. 审核通过时，在同一事务中更新订单状态并创建或更新有效权益。
8. 审核拒绝时记录原因，不能创建权益。
9. 重复审核返回已处理结果或冲突，不得重复授予权益。
10. 所有订单审核写入审计日志。

### 6.5 权益规则

权益由服务端计算和授予。前端的 `freeAccess`、商品状态、按钮状态或本地字段不能独立解锁课程。

有效权益需要满足日期范围约束，数据库已有有效期顺序检查和活跃权益唯一索引。删除课程、下架商品或停用账号时必须分别确认对历史订单、既有权益和学习记录的影响，不能级联误删财务或合规记录。

## 7. 入学测评与题库流程

### 7.1 题库

题目字段包括科目、题型、题干、选项、正确答案、分值、解析、知识点和状态。

约束：

- 单选题只能有一个正确答案。
- 多选题必须使用答案数组。
- 判断题、选择题必须有至少两个选项。
- 填空题和主观题不能设置选项。
- AI 生成题目必须先为草稿，不能直接发布。
- 题目修改必须保留必要的审计和版本语义，已被试卷快照引用的题目不能无痕改变历史考试含义。

### 7.2 试卷

创建试卷时必须校验试卷 ID、标题、时长和题目 ID 列表。试卷项目保存题目快照，确保日后题库题目变更不影响已分发试卷的历史内容。

只有已发布试卷才允许分发。

### 7.3 分发

1. 教师选择已发布试卷和学生。
2. 后端查询学生和试卷，校验数据存在。
3. 生成随机分享 token，只保存哈希，不保存明文 token。
4. 返回一次性的分享 token 给教师前端用于生成链接。
5. 同一学生和试卷的分发通过唯一逻辑和事务处理，重新分发会重置到待开始并生成新 token。
6. 操作写入审计日志。

### 7.4 访问、开始和提交

- 公开链接必须同时匹配试卷 ID、token 哈希和有效分发记录。
- 不向公开考试响应返回 `share_token_hash` 等内部字段。
- 已提交、已撤销或已超时分发不可再次答题。
- 超过开始截止时间且尚未开始的考试不可开始。
- 开始操作使用行锁，重复开始不得重置截止时间。
- 开始后创建固定的 `exam_deadline_at`，当前默认时长由试卷设定。
- 提交操作使用行锁、事务和唯一约束，重复提交返回已有结果或冲突。
- 当前服务端实现会拒绝超过考试截止时间的提交；如果产品要求“自动按超时交卷”，必须先修改产品规则、前后端状态枚举、测试和文档，再实现，不得只改一端。
- API 模式公开测评前端只负责加载服务端题目快照、发起开始和提交请求；不信任浏览器传入的学生 ID、固定规则 token 或本地评分结果。
- 客观题由服务端评分；主观题保持待批改状态，不能由浏览器自行宣布最终分数。
- 本地演示模式仍保留独立的本地测评分支，但该分支只允许用于无真实数据的界面演示，不得与 API 模式混用。

## 8. 学习计划、任务、自测与学习事件

### 8.1 计划复制原则

学生计划必须是模板发布版本的副本。教师后续修改模板不能回写已经分配的学生计划。个性化调整写入学生计划或附加任务，不修改公共模板。

### 8.2 今日任务推进

学生首页按完成进度而不是固定日历推进：

1. 每个解锁计划找到第一个尚未全部完成的行。
2. 行内已完成项保持完成状态。
3. 未完成项次日继续出现。
4. 只有一整行全部完成后才推进到下一行。
5. 前置计划未完成时，后继计划不解锁。
6. 未来 7 天从当前活跃行向后展开。
7. 休息日只暂停推送，不改写计划副本和学习日计数。

### 8.3 休息日

`restWeekday` 使用 `0` 到 `6`，与 JavaScript `Date.getDay()` 一致；未设置和取消后都是 `null`。

API 模式下，休息日必须通过 `PATCH /api/students/:id/preferences` 写入 `student_learning_preferences`，服务端返回规范化的 `restWeekday` 和 `restWeekdaySetAt` 后，前端才更新内存状态。保存期间必须禁用重复点击，失败时不得伪造成功状态。本地演示模式可以保留本地状态，但不能作为生产数据来源。

设置必须提前至少一天生效。只有设置时间早于当日本地 00:00 且星期匹配时，当天才是休息日。休息日首页和今日计划只展示固定问候，不推送任务和日周月自测。取消后立即恢复正常推送。

### 8.4 日周月自测

学生日、周、月自测结果必须保存成绩、总分、答案快照和错题。API 模式下学员科目和自测推送偏好通过学生偏好 API 持久化；付费学生默认开启三种推送，但人工关闭后必须持久化 `optedOut=true`，不能因重新识别付费身份自动打开。当前偏好 API 已支持报考科目、休息日和 `assessmentPush` 的部分更新，计划调整自动化、草稿和历史仍需继续补齐写入闭环。

同一学科的推送优先级为月测大于周测大于日测。政治、英语、数学的题型和数量遵循 `ARCHITECTURE.md` 中的学科规则。

### 8.5 学习事件

关键学习行为应逐步写入 `learning_events`，包括视频开始、视频完成、任务完成、答题、自测提交、单词复习和工具会话完成。事件至少包含学生、工具、事件类型、发生时间、科目、知识标签、payload 和 schema version。迁移 008 已增加 `event_key`、`tool_id`、`knowledge_tags` 和 `schema_version` 字段，并为学生事件键建立唯一索引；现有路由尚未覆盖全部事件写入。

事件不能包含密码、模型密钥或不必要的个人敏感信息。高频事件需要限流、批量写入或异步队列设计。事件写入必须考虑幂等键，避免刷新、重试或重复点击制造重复学习记录。

### 8.6 API 模式计划恢复

学生登录或刷新后，前端必须请求 `GET /api/students/:id/plans`，以服务端返回的计划和任务完成记录恢复 `assignedPlans`。服务端返回的 snake_case 字段必须经过归一化，任务完成状态以 `task_completions` 为准，不得仅依赖 localStorage 或初始空数组。

当前已完成计划读取与任务完成状态回填；计划结构编辑、删除/归档、版本并发控制、调整草稿和调整历史的服务端写入仍未完成。任何新增计划编辑功能都必须先补充 API、权限、审计和迁移设计。

## 9. 社区内容与审核

帖子创建后不能直接对所有用户公开，必须经过审核状态机。当前审核角色为 admin、teacher、assistant，但 assistant 的权限范围应继续按正式权限矩阵确认。

AI 预审只能生成风险标签、置信度和依据，最终公开、驳回和删除由规则或管理人员决定。审核必须保存操作人、时间、决定和原因。

展示用户内容时必须防止 HTML/脚本注入。不要把未经清洗的用户内容放入 `dangerouslySetInnerHTML`。若必须支持 Markdown 或富文本，应采用明确的白名单清洗器和测试用例。

## 10. 文件、导入和对象存储

### 10.1 Excel 导入

所有前端 Excel 导入必须使用 `readWorkbookSafely`，不能在业务组件中直接调用 `XLSX.read`。

共享解析器当前限制：

- 文件大小最多 10 MB。
- 首个工作表必须存在。
- 工作表范围必须可解析。
- 数据行最多 10000 行。
- 关闭公式、HTML、样式、VBA、额外文件加载等不必要能力。
- 读取失败必须转为用户可理解的错误提示。

导入后还必须进行列名、单元格内容、空行、数量和字段长度校验。不能因为 Excel 文件能打开就认为数据可信。SheetJS 当前存在已知高风险依赖问题，后续应评估替换、隔离、服务器端解析或限制可接受文件类型。

### 10.2 对象存储

`server/src/storage.js` 通过驱动适配对象存储。当前 local 驱动可以保存、读取、统计、删除和生成签名 URL，s3、oss、cos 驱动尚未配置真实实现。

对象键必须经过 `sanitizeKey`，不能包含路径穿越。签名 URL 使用 `SESSION_SECRET` 生成带过期时间的 HMAC，并绑定精确对象键；验证必须检查过期、签名长度和 timing-safe equality。

文件访问必须同时检查：

- 调用者身份。
- 业务资源归属或课程权益。
- 对象是否存在。
- 文件 MIME、大小和用途。
- 签名 URL 的过期时间。

任何上传、下载、删除和公开动作都应写审计日志，并规划病毒扫描、MIME 检测、内容处置和删除清理。

### 10.3 浏览器对象 URL

前端使用 `URL.createObjectURL` 时，必须在文件被替换、组件卸载或不再使用时调用 `URL.revokeObjectURL`。新增文件预览功能必须同时设计创建和释放路径，避免长时间运行页面的内存泄漏。

## 11. AI 监管机器人设计

AI 能力必须由后端统一编排，浏览器不能直接携带模型密钥调用供应商。

教师端使用一级入口“监管机器人”，不把模型槽位混入系统设置。机器人配置至少包括：

- `provider`
- `model`
- `endpoint`
- `secretRef`
- `enabled`
- `systemPrompt`
- `restrictionWords[]`

真实密钥只能存在服务器环境变量或密钥管理服务；前端只看到是否就绪、模型名称或脱敏信息。

当前规划中的机器人包括：`periodic_assessment`、`entrance_grading`、`plan_assistant`、`learning_report`、`community_moderation`、`document_ocr`、`handwriting_grade`、`question_tutor`、`embedding`。

所有 AI 输出必须经过：

1. 权限检查。
2. 输入数据范围检查。
3. 敏感信息脱敏。
4. prompt 版本记录。
5. 供应商和模型记录。
6. 超时、限流和失败处理。
7. 结构化输出校验。
8. 业务规则校验。
9. 必要的人工审核。
10. `ai_jobs` 和审计记录。

AI 不能直接改变学生权益、订单状态、最终考试成绩、课程发布状态或社区公开状态。AI 只能生成草案，除非已有明确的、可测试的自动规则允许自动生效。

`question_tutor` 必须使用可读图的多模态模型；纯文本模型不能直接读取图片。若使用 OCR + 文本模型，必须把 OCR 结果作为可追溯快照保存，并允许用户知道识别可能存在误差。

## 12. API 请求和错误处理标准

所有浏览器 API 请求通过 `src/api.js`：

- `credentials: 'include'`。
- 自动设置 `Accept` 和 `Content-Type`。
- 非 GET/HEAD 请求增加 `X-Requested-With: XMLHttpRequest`。
- 非字符串 body 自动 JSON 序列化。
- 默认 15 秒超时。
- 401 派发 `shangan:auth-expired`。
- 5xx 派发 `shangan:api-error`。
- 统一抛出 `ApiError`，包含 status、code、details 和 requestId。

后端错误响应结构为：

```json
{
  "error": "面向用户的错误信息",
  "code": "错误代码",
  "details": [],
  "requestId": "请求 ID"
}
```

生产环境不向用户返回堆栈、SQL、环境变量、密钥、内部路径或数据库结构。日志中必须对密码、Cookie、token、session、shareToken 等字段脱敏。

每个请求必须有安全的 request ID。客户端提供的 `X-Request-ID` 只能在符合允许字符和长度时使用，否则生成随机 UUID。响应通过 `X-Request-ID` 返回，便于排查。

## 13. 安全设计基线

### 13.1 必须保持的安全控制

- 生产环境 `SESSION_SECRET` 至少 32 位，且必须是随机强值。
- 生产 `APP_ORIGIN` 必须是无路径的 HTTPS origin。
- CORS 只能允许明确 origin，不能使用 `*` 配合 credentials。
- Session Cookie 必须 HttpOnly；生产必须 Secure；SameSite 保持受控策略。
- 所有 SQL 使用参数化查询。
- 所有 body、params、query 使用 Zod 或等效严格 schema。
- 所有写操作检查角色和资源归属。
- 课程、商品、订单、权益和考试关键状态由后端决定。
- 关键并发操作使用事务、行锁和唯一索引。
- 所有敏感操作写审计日志。
- 服务器启动不能接受缺失或弱密钥。
- Vite 本地服务只监听 `127.0.0.1`，模型桥接目标必须在白名单中。
- 不允许把模型密钥、支付密钥、对象存储密钥放入前端或 localStorage。
- 不允许未经清洗地渲染用户 HTML。
- 不允许通过 localStorage 作为正式认证或正式权益来源。

### 13.2 当前已知风险

- API 模式下报考科目、休息日和部分自测推送偏好已经有服务端受限 API；计划结构编辑、AI 调整历史、完整学习事件写入和部分学习进度操作仍未完全云端闭环。
- API 模式已经禁止注入演示学员并在档案缺失时展示受控空态，但本地演示账号和默认演示数据仍存在于前端代码，生产必须确保不进入真实运行路径。
- `xlsx` 依赖存在高风险漏洞且上游暂时没有直接修复，需评估替换或服务端隔离。
- 尚无完整 PostgreSQL 集成测试环境；迁移 007、008 尚未在真实数据库完成执行验证。
- 尚无正式 CSRF token 体系；当前依赖 SameSite Cookie、严格 CORS 和 X-Requested-With，正式上线前应按部署拓扑复核。
- assistant/operator 的字段级权限仍需形成正式矩阵。
- 对象存储真实云驱动、文件扫描、支付回调、AI 编排和知识库尚未完成。
- Vite 构建仍有大 chunk 警告，需要后续做代码分割和性能分析。
- 入学考试逾期提交的产品规则需要最终确认。

这些风险必须在本文件中保留，不能为了让“上线完成”看起来更完整而删除。

## 14. 标准开发执行流程

每一个新需求都必须按以下步骤执行。

### 第一步：明确需求和边界

写清楚用户、页面、接口、数据表、角色、状态和外部依赖。判断需求是新增功能、修复 bug、安全加固、重构、迁移、部署还是清理文件。

必须明确“不做什么”，防止模型扩大修改范围。

### 第二步：定位真实代码

先读取相关入口和调用链，不要只搜索一个文件名。至少检查：前端调用点、API 路由、schema、数据库表、DTO、错误处理、测试和部署配置。

如果是数据问题，必须同时看前端字段名和后端返回字段名；如果是权限问题，必须同时看路由 preHandler、资源归属判断和数据库查询条件。

### 第三步：写出执行方案

执行方案必须包含：

- 修改文件。
- 现有行为。
- 目标行为。
- 数据和权限影响。
- 失败路径。
- 并发和幂等处理。
- 测试方案。
- 是否需要迁移。
- 是否需要更新本文件和其他契约文档。

### 第四步：先修改最小必要范围

优先使用现有 helper、schema、DTO、storage adapter 和错误处理。不要重复造一套认证、权限、归一化、导入或日志逻辑。

不要顺手重写无关的巨型组件。对于 `src/App.jsx` 等大文件，先定位小范围函数，分段修改并在每次修改后检查语法。

### 第五步：补齐服务端规则

只在前端校验不够。凡是涉及账号状态、课程发布、商品上架、订单、权益、考试、计划归属、社区审核和 AI 生效，都必须在后端再次校验。

### 第六步：补测试

## 15. Bug 修复流程

遇到页面直接报错时，按以下顺序处理：

1. 记录复现入口、用户角色、操作步骤和错误信息。
2. 检查是否为 localStorage/API 返回结构异常、undefined 数组、null 对象或字段命名不一致。
3. 在渲染边界做安全归一化，但不要掩盖服务端契约错误。
4. 如果错误来自 API，检查后端 DTO 和前端 normalize 函数。
5. 如果错误来自状态写入，检查数据初始化、刷新、登出和 API 模式门控。
6. 修复后测试首次进入、刷新、空数据、错误数据、权限不足和移动端。
7. 将根因、修复和回归结果写入变更记录。

所有持久化数据都必须被视为不可信输入。数组、对象、映射、课程 ID、分类列表和 API 响应在进入渲染和 mutation 前必须做类型和形状检查。

## 16. 部署执行流程

### 16.1 上线前准备

上线前必须先区分“预发布联调”与“正式生产上线”。当前项目只满足进入预发布联调，不满足无验证直接对外生产使用。

预发布至少执行：

1. 准备隔离的 PostgreSQL 实例或 Docker 数据库。
2. 使用迁移 runner 按顺序执行 `001` 至 `008`，确认 `schema_migrations` 记录完整，特别检查 `007` 复合主键和 `008` 学习偏好/事件索引。
3. 使用独立测试账号验证管理员、教师、学生和公开考试访问，不得使用真实学生数据做首次联调。
4. 生成强随机 `SESSION_SECRET`，设置 `APP_ORIGIN` 为正式 HTTPS origin。
5. 设置 `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`。
6. 检查 `.env` 不在源码提交或前端静态目录中。
7. 运行 `sh scripts/verify-predeploy.sh`。
8. 检查镜像、依赖锁文件和迁移文件。
9. 准备独立备份存储和恢复目标数据库。
10. 完成登录、首次改密、权限隔离、课程/订单、公开测评、偏好和计划刷新恢复冒烟测试。

正式生产还必须在预发布通过后，补充域名、HTTPS、反向代理、对象存储、支付、监控、告警和备份恢复演练。

### 16.2 Docker Compose 启动顺序

1. `db` 启动并通过 PostgreSQL 健康检查。
2. `migrate` 等待数据库健康后执行一次迁移。
3. 迁移失败时，`api` 不得启动。
4. `api` 启动并通过 `/ready` 数据库就绪检查。
5. `web` 在 API 健康后启动并由 Nginx 提供静态页面和代理。
6. 运行 `docker compose ps` 和 `docker compose logs -f migrate api web`。
7. 检查 `/health` 与 `/ready`。

不能把 migration 自动塞进每个 API 实例的启动命令，也不能在正式启动时自动创建管理员。

### 16.3 管理员初始化

迁移完成后单独运行 `bootstrap-admin`。初始账号默认强制首次改密。完成登录和改密后清理临时环境变量、shell 历史和部署记录中的临时密码。

### 16.4 备份恢复

每日执行 `scripts/backup-db.sh`，备份至少保留 14 天并复制到独立存储。恢复必须使用独立目标数据库，先运行恢复脚本和业务冒烟，再决定是否切换流量。正式上线前必须完成一次可记录的恢复演练。

## 22. 最终执行原则

本项目的正确标准不是“页面能打开”，而是：数据有来源、权限有边界、状态有约束、写入可幂等、失败可恢复、操作可审计、部署可验证、备份可恢复、模型可交接。

在任何功能便利性和生产安全发生冲突时，优先保证：

1. 不泄露认证凭证和服务端密钥。
2. 不让前端伪造权益、成绩、账号状态或审核结果。
3. 不破坏已有用户数据和历史记录。
4. 不绕过数据库约束和事务。
5. 不让未验证的 AI 输出直接生效。
6. 不让未确认的临时文件清理影响源码、配置或业务数据。
7. 不让文档与代码长期出现互相矛盾的状态。

本文件是持续维护文件，不是一次性说明。后续所有模型都必须把它作为执行入口，并在每次实际修改完成后及时更新。
