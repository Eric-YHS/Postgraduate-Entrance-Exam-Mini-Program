## 1.1 交互状态真实性

教师端和学生端的按钮、弹窗、保存、审核、提交和返回操作必须与真实业务结果一致。只读说明窗口只能提供“知道了/关闭”，不得使用“确认并保存”等会暗示写入的按钮。API 模式下，任何尚未具备服务端接口的本地草稿、Blob URL、模拟 AI 结果或本地错题记录，都必须明确提示不会写入服务端；不得在请求未成功时显示“已保存”“已开通”或“已生成”。统计数量没有后续动作时渲染为普通信息，不得伪装成可点击入口。

本轮已修复的交互包括：教师工作台登记队列刷新改为服务端读取，社区和订单批量审核改为复用现有审核接口，学生端未就绪的题目讲解不再显示为可用工具，通用能力弹窗改为只读说明，API 模式禁止浏览器保存模型凭证和机器人配置；教师端个人计划编辑和删除已接入服务端 revision 版本控制及冲突提示，入学测评和日/周/月自测错题可进入服务端归档，学生手动标记错题也会通过受保护接口写入云端。真实 AI 推理、课程资源云端上传、病毒扫描、知识库检索和计划附件持久化仍属于未完成的服务端能力。

## 2. 运行模式与总原则

系统存在两种模式。

API/预发布或生产模式由 `VITE_API_BASE_URL` 配置启用。浏览器通过 Fastify API 访问 PostgreSQL，认证使用 HttpOnly Cookie，课程、商品、订单、权益、学生档案、考试、计划和偏好以服务端数据为准。任何核心操作都不得以 localStorage 作为最终依据。

本地演示模式仅用于界面调试、无敏感数据的功能演示和离线原型。该模式可能包含演示学生、localStorage 和本地考试分支，不得用于真实学生、真实订单、真实考试或正式运营。

所有角色都应遵循以下原则：前端按钮只代表操作入口，不代表权限；服务端是权限、状态和数据校验的最终裁决者；业务写入失败时不得在页面上伪造成功；重复点击、网络重试和页面刷新不得造成重复权益、重复考试提交或重复学习记录。

## 3. 角色与权限边界

系统角色包括 `admin`、`teacher`、`assistant`、`operator` 和 `student`。

管理员负责账号、审计、全局配置和全部教师能力。教师负责学生、课程、商品、订单审核、学习计划、题库、试卷、测评发放和社区审核。助教与运营人员只能获得其路由明确允许的读取或辅助能力，不应因为同属 staff 而自动拥有课程发布、订单审核、账号管理或学生敏感字段写权限。学生只能访问自己名下的档案、课程权益、订单、计划、任务、自测、学习偏好和社区内容。

前端必须按角色隐藏无关入口以减少误操作，但后端必须在每个接口再次验证角色、账号状态、资源归属和字段级权限。学生请求学生资源时必须匹配当前会话中的 `studentId`；找不到自己的档案时页面只能展示受控空态，不得回退显示任意其他学员数据。

## 4. 认证、会话与改密操作逻辑

### 4.1 登录

用户通过手机号和密码登录。服务端校验参数、查询启用账号并使用 Argon2id 校验密码哈希。成功后服务端写入 HttpOnly `session` Cookie，前端只保存非敏感的当前账号摘要。登录失败不得暴露账号是否存在、账号是否被禁用或密码具体错误。

每次业务请求都由服务端读取 Cookie 中的 JWT，并回查数据库的账号状态、角色、关联学生和强制改密状态。因此，管理员停用账号后，即使浏览器仍保存旧 Cookie，也不能继续访问业务接口。

### 4.2 首次改密与管理员重置

管理员初始化或重置账号密码后，可将账号设为“必须改密”。这类账号登录后只能读取当前身份和调用改密接口，普通业务接口应返回拒绝。

用户改密必须输入当前密码和不少于 12 位的新密码。API 模式下，前端必须调用 `POST /api/auth/change-password`，成功后重新请求 `GET /api/auth/me` 获取最新会话身份；不能只在浏览器内修改展示状态。改密失败时保留当前表单并提示失败原因，不得自动退出或显示“修改成功”。

### 4.3 退出、账号停用与读取失败

退出登录时调用已认证的服务端登出接口清理 Cookie，并写入退出审计后再清理前端非敏感会话状态。若登出请求因网络或服务器错误未获确认，前端必须保留当前会话并提示用户重试，不能把页面切回登录页而让有效 Cookie 仍留在浏览器中。管理员或教师停用学生账号时，历史订单、测评、计划和审计记录必须保留；重新启用后可恢复登录，但不应无审计地改变既有权益或成绩。

学生端读取档案或学习计划失败时，页面必须清空未完成的加载数据，明确显示失败原因和“重新加载”操作；不得将局部失败伪装成“暂无计划”，也不得回退到演示学员、默认账号或列表首项。

## 5. 学员档案、报考科目与学习偏好

### 5.1 学员档案读取

学生登录后，前端只请求自己的 `GET /api/students/:id`。教师或受权员工请求学生列表或指定档案。服务端返回基础档案以及已迁移的学习偏好数据，包括报考科目、休息日和自测推送设置。

API 模式中，学生端必须在档案与计划加载完成前显示加载状态；读取失败时清空本轮不完整数据，展示失败原因和“重新加载”操作。不得用演示账号、默认账号、列表首项或“暂无计划”替代真实失败状态。

### 5.2 档案修改

学生自助修改仅限姓名、邮箱、收货信息、学校和目标分等明确允许字段。助教只可维护同样的基础联络字段；运营人员不可修改学生档案。管理员和教师可在受控 schema 内维护学习阶段、学情评价、学员类型和付费截止等业务字段。学生不能修改身份、付费状态、权益、角色、计划归属、账号状态或最终成绩。教师修改档案时应使用受控字段 schema，并在服务端写入审计日志。学生账号与扩展档案必须由 `POST /api/admin/students` 的同一服务端事务创建，临时密码由服务端随机生成、仅成功响应一次性返回且首次登录必须改密；不得在生产路径使用固定默认密码。

### 5.3 报考科目与学习偏好

学习偏好数据由 `student_subjects` 和 `student_learning_preferences` 保存。读取使用 `GET /api/students/:id/preferences`；学生修改自己的报考科目、休息日或自测推送使用 `PATCH /api/students/:id/preferences`。管理员或教师为学生代设自测推送时也使用该接口，服务端必须审计、返回规范化结果并以服务端返回值刷新页面；助教和运营人员不得借此修改学习偏好。

前端提交偏好时必须显示保存中状态并禁用重复点击。服务端返回的规范化结果才是页面后续状态来源。失败时前端保留原状态并提供清晰错误信息。教师当前可读取受权学员的偏好；是否允许教师代为修改需在新增接口前明确产品规则、权限和审计逻辑。

### 5.4 每周休息日

休息日使用星期编号 `0` 至 `6`，与 JavaScript `Date.getDay()` 一致。`null` 表示未设置或已取消。设置后使用服务端返回的 `restWeekdaySetAt` 判断是否满足提前一天生效规则：当天临时改选当天休息日时，今天不暂停任务，从下一个对应星期开始生效；取消后立即恢复正常任务推送。

休息日不会删除或改写计划任务。当天只暂停任务和日周月自测的主动推送，下一学习日仍从未完成任务继续推进。

## 6. 课程、商品、订单与权益

### 6.1 教师创建课程和商品

教师创建课程时填写名称、科目或受众、分类、描述、定价和状态。服务端校验字段长度、价格和允许状态。课程应先保存为草稿，满足发布条件后由教师执行发布操作。

商品可以绑定单门课程、组合课程或资料。发布商品前，服务端必须确认商品价格正确、至少绑定一门课程、所有课程存在且已发布。浏览器传入的课程状态、价格或金额不能作为最终依据。

### 6.2 学生查看与购买

学生读取可见课程和商品。公开课程可直接展示；付费课程必须由有效权益控制。当前实现还允许与已报名科目匹配的已发布课程进入可见范围，正式运营前必须按产品规则确认“报名科目可见”是否等同于“获得付费访问权”，避免把可见性误当成授权。

学生下单必须提交真实商品 ID，不能用课程 ID 伪造商品。服务端根据商品查询价格和绑定课程：免费商品可自动形成已支付订单并授予权益；付费商品形成待支付或待审核订单，等待人工审核或未来支付回调。

### 6.3 审核与权益发放

教师或管理员审核订单。通过时，服务端在同一事务中更新订单状态并创建或更新有效权益；拒绝时只记录审核结果和原因，不产生权益。重复审核不得重复授予权益。

订单、权益和关键审核操作使用数据库约束、事务和幂等基础保护。浏览器发起非读取请求时会生成 `Idempotency-Key`；同一调用主体使用同一键重试相同请求可获得原响应，不同主体不会相互复用响应。当前仍需真实 PostgreSQL 并发测试验证该逻辑。

## 7. 学习计划、任务与进度

### 7.1 教师分配计划

教师从计划模板选择科目计划后，为指定学生生成副本。学生计划保存自己的 rows，不会因后续模板修改被无声改写。计划可以声明前置计划，前置计划未完成时后继计划不能解锁。

“开始的位置”即 `startDay`，只表示该计划从任务表内部的第几天开始，不能用来表达自然日期等待。教师可为每个学员任务组合单独设置可选的“任务开始日期”（`startDate`，`YYYY-MM-DD`）；该日期当天按 Asia/Shanghai 日期解锁。日期未到时，该组合不进入学生的今日、未来或完整任务计算；日期为空则保持原有逻辑。若同时设置前置计划和开始日期，必须同时满足“前置已完成”与“已到开始日期”才可执行。学生端应明确显示预计开始日期，服务端也会拒绝开始日期之前的任务完成请求，不能仅依赖前端隐藏任务。

创建计划时服务端校验学生存在、科目、名称、任务行和前置计划归属。教师端创建成功后应使用服务端返回的计划 ID 更新页面，而不是继续使用本地时间戳作为正式 ID。

### 7.2 学生任务展示

学生端通过 `GET /api/students/:id/plans` 加载计划与 `task_completions`，然后恢复每行任务完成状态。今日任务取每个已解锁计划中第一个未完全完成的任务行：已完成项不再重复出现，未完成项次日继续，整行任务完成后才推进下一行。未来任务从当前活动行向后展开。

### 7.3 任务完成与撤销

学生点击完成任务时，前端先检查是否为休息日，再调用 `POST /api/plans/:id/tasks/:rowIndex/:taskIndex/complete`。撤销时调用同一路径的 `DELETE`。服务端必须验证计划归属当前学生、行索引和任务索引有效，并通过唯一约束防止重复完成记录。

前端应在请求期间禁止重复点击。请求成功后以服务端结果更新页面；请求失败时保持原有完成状态并提示重试。当前任务完成接口已存在，但任务完成后的学习事件、计划自动调整草稿和完整的稳定重试键仍需继续完善。

### 7.4 计划编辑边界

当前已完成计划创建、读取和任务完成记录。计划结构编辑、删除/归档、附件、前置关系变更、版本控制、冲突处理、AI 调整草稿和调整历史仍未形成完整服务端写入闭环。

在这些接口完成前，不能把教师端本地修改视为学生刷新后仍可恢复的正式数据。新增该类能力时必须同时设计 API、数据库迁移或版本字段、角色权限、前置环检测、审计、幂等和前后端错误状态。

## 8. 自测、入学测评与测评档案

### 8.1 日、周、月自测

学生自测记录包含测评类型、科目、标题、得分、总分、答案、错题和批改时间。学生提交自测后由服务端写入 `assessment_records`。学生或教师读取档案时应按学生归属验证。

日周月推送的开关数据属于学习偏好。付费学生可以默认开启，学生人工关闭后必须保留关闭状态；月测优先于周测，周测优先于日测。教师或管理员代设时必须调用服务端偏好接口并以返回值刷新，不能只改前端状态。当前自动推送调度、教师端完整刷新恢复与真实环境验证仍需进一步完成。

### 8.2 公开入学测评分发

教师选择已发布试卷和学生后，调用分发接口。服务端生成随机 token，只保存 hash，并把一次性明文 token 返回给教师用于生成分享链接。分享链接格式为 `/exam/{paperId}?token={shareToken}`，不得携带学生 ID、学生手机号、答案或固定可推导 token。

重新分发同一学生和试卷时，服务端重置到待开始并生成新 token。旧链接不可继续视为有效凭证。教师复制链接后应通过安全渠道发给该学生，不应公开发到群聊或论坛。

### 8.3 公开链接访问、开始与提交

学生打开公开链接时，前端请求 `GET /api/exams/:paperId/:token`。服务端验证试卷、token hash、分发状态和开始期限，成功后写入 HttpOnly `exam_session` Cookie，并只返回公开题目快照和必要分发信息。

学生点击开始后，前端调用 `POST /api/exams/distributions/:id/start`。服务端使用行锁保证重复点击不重置计时，并写入固定答题截止时间。答题页面只展示服务端返回的题目；浏览器不应保存正确答案，也不应自行判定最终得分。

学生提交后，前端调用 `POST /api/exams/distributions/:id/submit` 并发送答案。服务端验证会话、分发归属、开始状态和截止时间，在事务中评分客观题、保存提交、写入测评档案和学习事件。主观题应保持待批改状态。提交成功后页面显示已提交，不允许再次作答。

当前服务端对超过答题截止时间的提交返回拒绝。若产品需要自动交卷，必须先定义答案保存机制、状态规则、超时提示和完整测试，不能只在前端加倒计时。

### 8.4 测评异常处理

公开链接无效、已提交、已撤销或开始期限已过时，应显示“链接不可用”并引导联系教师重新分发。考试加载、开始和提交均应显示等待状态；提交失败时保留当前答案并允许用户重试。网络中断或浏览器关闭后答案自动保存能力尚未实现，不能向学生承诺草稿恢复。

## 9. 社区内容与审核

学生和员工可以提交学习社区帖子。帖子默认进入待审核状态；只有审核通过后才向其他用户公开。学生可查看自己的待审核内容，但不能查看其他学生的待审核内容。

教师、管理员和已明确允许的助教可以审核社区帖子。审核应保存审核者、审核时间、决定和原因。前端不得通过隐藏状态或本地变量直接将帖子变成公开。

用户内容以纯文本方式渲染。禁止直接将用户输入作为 HTML 注入；如未来引入 Markdown 或富文本，必须增加白名单清洗器和攻击用例测试。

## 10. 文件、导入与学习工具

Excel 导入只能使用共享的 `readWorkbookSafely` 解析器。文件最大 10 MB，首个工作表和工作表范围必须有效，行数不超过 10000，并禁用不需要的公式、HTML、样式、VBA 与外部能力。导入后的字段、列名、长度和空值仍需进行业务校验。

API 模式下的学员 Excel 导入必须先在浏览器完成安全解析和行结构检查，再调用 `POST /api/admin/students/import`。每行必须具备姓名、11 位手机号及可创建账号所需字段；服务端会再次使用受控 schema 校验，并在一个事务中创建全部学员档案、账号、科目关系和一次性临时密码。导入数据内部手机号重复、与既有账号冲突或任一行不合法时，整批回滚，不得显示局部成功或把“待填写”写入真实手机号字段。临时密码只在成功响应中显示一次，教师必须通过安全渠道转交并要求首次登录改密。

### 10.1 代学题库与计时学习

“代学”使用独立题库，不与知识库上传、入学测评题库、自测题目或错题档案自动合并。教师或管理员在“带背后台”选择政治、英语或数学，填写书籍名称与状态后，通过 Excel 批量导入题目。Excel 首工作表使用“题号、题干、学习时长（秒）、知识点、半程提示、答案、解析”列，状态为可选列。浏览器必须先使用 `readWorkbookSafely` 解析，文件不超过 10 MB、行数不超过 10000；服务端再次校验字段、题号唯一性和每题 60 至 86400 秒的时长，并在一个事务中写入书籍和题目。重复导入同一科目和书名时更新同题号配置，导入请求必须保留幂等保护并写审计。

学生在“学习工具”打开“代学”后，只能查看与自己已报名科目一致的已发布书籍和已发布题目。题目列表不会返回知识点、半程提示、答案或解析。学生选定基础、适中或合适做题风格后开始会话，服务端分别按原始时长的 2 倍、1.5 倍或 1 倍记录有效时长。页面顶部显示服务端返回的剩余时间；剩余十分钟以内才能显示知识点，经过总时长一半才能显示半程提示，到时才能显示答案与解析。学生点击“提前结束”后，服务端持久化结束原因并返回已解锁答案；“上一题”和“下一题”会开启目标题目的新会话，不可将上一题会话本地伪装成下一题结果。

书籍或题目为草稿、已归档，或学生未报名对应科目时，学生端不得显示或通过接口获取。加载失败必须显示错误与重新加载；开始、提前结束和导入期间必须禁用重复操作。当前 `012_companion_study.sql` 尚待真实 PostgreSQL 执行与浏览器端到端验收，不能在运营中表述为已完成正式生产验证。



题目辅导、OCR、AI 批改和知识库目前不能被描述为真实可执行 AI 服务。服务端已提供 AI 机器人注册表和任务记录基础，管理员可记录机器人能力、Provider 引用、提示词、限制词、工具白名单及人工审批要求；创建任务时会校验调用角色、学生归属、机器人状态与输入大小，并写入审计。该基础不保存模型 API Key，也不执行外部模型调用。真实 AI 调用必须在服务端执行，并具备 Provider 配置与密钥引用、prompt 版本、结构化输出校验、任务执行器、失败重试、成本记录、人工审核和审计；AI 不得直接修改订单、权益、最终成绩、课程发布或社区公开状态。

## 11. 统一异常处理逻辑

页面应至少具备 Loading、Empty、Error、Success 和 Pending 五类状态。课程/商品、订单和社区等服务端读取失败时，前端不得把失败伪装成空列表：学生课程、商城、社区页面以及教师课程与商品、社区审核页面应显示可理解的错误、保留重新加载入口，并在重试成功后以服务端返回值刷新对应数据域。教师端课程与商品页面同时承载订单审核，因此订单读取失败提示应在该页面显示；社区读取失败提示应在社区和社区审核页面显示。任何异步按钮在请求期间应禁用，防止重复点击。失败时显示用户可理解的原因与可执行的下一步，不显示 SQL、堆栈、密钥、Cookie、内部路径或数据库细节。

`401` 表示会话失效，前端应清理会话并回到登录流程。`403` 表示当前账号无权操作，页面不应继续展示受保护数据。`404` 表示目标不存在或已被删除。`409` 常用于重复提交、并发冲突或幂等键冲突，应提示用户等待、刷新或使用同一操作的重试。`422` 通常表示字段或状态不符合业务规则，应保留用户输入并指出需修正的内容。`5xx` 表示服务端异常，应记录 request ID 并提示稍后重试。

所有敏感操作如账号状态变更、订单审核、试卷分发、学习偏好修改和计划创建都应写审计日志。日志必须脱敏密码、token、Cookie、会话和密钥。

## 12. 预发布操作逻辑

当前系统可以进入预发布联调，不应未经验证直接面向真实用户正式上线。

预发布首先准备隔离 PostgreSQL。使用迁移工具按顺序执行 001 至 012 号迁移，确认 `schema_migrations` 完整记录每个文件。特别验证 007 号迁移是否成功将幂等键调整为 `(principal_id, idempotency_key)` 复合主键，008 号迁移是否创建学生科目、偏好和学习事件索引，010 号迁移是否加入计划开始日期，011 号迁移是否加入 Provider、计划 revision 与错题归档表，以及 012 号迁移是否创建独立代学书籍、题目和会话表。

迁移完成后单独初始化管理员账号，使用临时密码登录，并验证强制改密。之后使用独立测试账号完成管理员、教师、学生和公开测评的完整冒烟流程：登录、退出、改密、学生档案读取、学习偏好保存、课程和商品可见性、免费订单或审核订单、权益发放、计划分配、任务完成与刷新恢复、试卷分发、公开链接、开始、提交和测评档案。

预发布还必须验证 HTTPS、反向代理 Cookie、CORS、`APP_ORIGIN`、`SESSION_SECRET`、健康检查、就绪检查、日志脱敏和容器重启后的数据持久性。每一步必须记录实际时间、操作者、环境、测试账号、结果、失败现象和 request ID。

## 13. 正式生产上线门槛

正式生产至少要求预发布核心流程通过，并补齐以下条件：生产 PostgreSQL 迁移成功且已备份；HTTPS、域名和反向代理已验证；对象存储和上传策略明确；支付流程或人工审核流程明确；监控、告警与日志保留策略启用；备份和恢复演练已完成；高风险权限、公开测评、订单权益和幂等并发已完成集成测试；部署后冒烟流程有可追溯记录。

以下能力尚未完成，不能在上线宣传或运营承诺中描述为已可用：真实 AI Provider 与 Agent Runtime、AI 自动改计划或评分、生产云对象存储与病毒扫描、自动支付回调、知识库向量检索、完整计划编辑持久化、浏览器端到端自动化验收和完整监控告警体系。
